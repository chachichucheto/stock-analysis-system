## 1. ハイブリッド調査

### 1.1 三層構造

| 層 | 担当 | 対象 | トークン | 頻度 |
|---|---|---|---|---|
| L1 広く浅く | Python(自動) | ニュース・開示・EDINET・株価の収集、イベント化、足切り | 0 | 1時間ごと〜毎日 |
| L2 候補ウォッチ | Python(自動) | 本命・監視の銘柄だけを対象に「新しい動き」を検知し、調査パックを作る | 0 | 毎日 |
| L3 深掘り | Claude(夜の手動セッション) | 新しい動きがあった候補と、新しく立てるシナリオだけを調べる | 大 | 毎晩(上限あり)+週1・月1 |

**トークンを使うのは L3 だけ**にし、L3 に渡す対象を L2 が絞る。これが頻度調整の中心。

### 1.2 L2 候補ウォッチ(新規に作る)

本命・監視の各銘柄について、前回の調査以降に次の新しい材料が出たかを、自動で数える(Python、トークン0)。

- TDnet・EDINET の新しい開示(銘柄コードで照合)
- 記事の見出しに、社名または証券コードを含むニュース(RSS・Google News・PR TIMES)
- 決算発表日が近づいた、崩れる条件のキーワードに当たる見出しが出た、など

結果は「動きあり/なし」と「新しい材料の一覧(見出し・URL)」。**「動きあり」の銘柄だけを L3 の対象にする。**

### 1.3 L3 深掘りのトークン管理

- **調査パック**:Python が銘柄ごとに、直近の開示・見出し・株価・決算日・前回の調査メモをまとめる。Claude はこれを読み、足りない点だけを Web 検索する(検索回数を減らす)。
- **予算**:1夜の Web 検索の上限を決める(案:新シナリオの上位1〜2件に計15回、動きありの候補に計10回、予備5回)。使い切ったら、翌日に回す。
- **調査メモの永続化**:調査結果は銘柄別のメモに残し、次回は差分だけ調べる。`next_check_date`(次に調べる日)を持たせ、それまでは調べ直さない。
- **頻度**:
  - 毎晩:当日のイベントと「動きあり」の候補だけ(最小手順は10分)。
  - 週1回:監視銘柄の一括の点検(L2 の結果を踏まえ、動きのない銘柄は省く)。
  - 月1回:振り返り。
- CONCEPT §14.2「必要になってから作る」に従い、L2 は**予行演習(フェーズE)で、夜の手作業の負担を見てから作る**。

### 1.4 自動では取れず、L3 の Web 検索が要るもの
業界統計・報道の本文・会社発表の詳細・SNS・海外の動き。ここはハイブリッドの手動側で扱う。

## 2. 既存システムとのデータ共有(二重取得をやめる)

### 2.1 原則
**データごとに「持ち主」を1つに決め、もう一方は読むだけにする。** 判断ロジック(スコア・レジーム・売買判断)は、互いに読まない(独立性)。共有するのは生データだけ。

### 2.2.1 ニュースは連想側を「大元」にする(ひろふみさん決定、2026-09-30)

前提: **ニュースの機械収集は連想モデルが担う。既存システムは、必要なら連想側を読み取り専用で参照する。**
統合(既存側の毎朝のニュース調査を、連想側の収集結果を読む形に変えること)は、**最後の統合の段階で相談する**。
それまでの設計上の約束:

- 収集結果は、連想側で完結した形で持つ(既存側に依存しない)。
- 共有棚のニュースの形式は、**既存側が後から読める安定した形**にする。
  列:`news_id, published_at(UTC), first_observed_at(UTC), source(フィード名), media(媒体名), tier(1公的〜4個人), title, url, summary, language`
  (`media` は `assoc.events.cluster.media_of` と同じ規則で付ける。Google News は実際の媒体名)。
- 日付ごとのファイル(`news_YYYYMMDD.parquet`)に**追記のみ**で出力し、過去の日のファイルは書き換えない。既存側は、
  最新日付と `manifest.json` の鮮度を見て読む(古ければ警告)。
- 既存システムの毎朝のニュース調査(平日6:30、CLAUDE.md の記載。実機のタスクは統合の相談のときに確認する)は、
  統合の段階で「連想側の見出しを先に読み、足りない分だけ Web 検索する」形に変える案を検討する。
  **その変更は既存側の変更なので、承認を得てから行う。**

### 2.3 仕組み(2つ)

1. **読む側のアダプタ**:既存ファイルの場所を `config.yaml` に書き、`PriceSource` などの読み取り部品から読む。**鮮度チェック**を必ず付け、既存のデータが古ければ警告する(古いデータを黙って使わない。既存の `daily_ohlcv` が7/24で止まっているのを、静かに使ってしまう事故を防ぐ)。
2. **共有棚(`data\shared\`)**:連想側が、毎日 CSV/Parquet を書き出し、`manifest.json`(作成日時・行数・列の定義・最新日付)を付ける。
   - DuckDB のデータベースを直接共有しない。DuckDB は書き込み中に他のプロセスが読めない。既存システムの日次処理(16:30)と衝突するため。
   - 既存側が読むかどうかは、既存側の判断(承認後)。

### 2.4 既存システムを変更するもの(承認が要る)
- 既存のスクリプトが、連想側の共有棚を読むようにする変更。
- 既存の日次パイプラインに、株価の更新(`cis_data_collect.py`)を足す変更。これは連想側が空白分を取得するので、当面は不要。

### 2.5 フォルダ間の連携について
- 連想モデルは、既存フォルダとは別フォルダに置かれているが、絶対パスの読み取りで連携できる(技術的な障害はない)。
- 読み取りは、既存側の処理(16:30の日次処理、研究計算)と同時に行っても、ファイルが書き換え中でなければ問題ない。書き換え中に読む事故を避けるため、読む前に更新時刻が数分間動いていないことを確認する。

5. 既存側の変更(承認後)
