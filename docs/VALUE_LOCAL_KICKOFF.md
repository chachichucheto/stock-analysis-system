# 割安カタリスト・モデル ローカル作業の指示書(ローカルの Claude Code 向け)

あなたは、ユーザーの Windows PC で動く Claude Code です。クラウドで設計・実装した「割安カタリスト・モデル」を、**実データで検証し、運用できる状態にする**のが仕事です。
(ニュース連想モデルの指示書は `docs/LOCAL_KICKOFF.md`。こちらは別のモデルです。両方を同じリポジトリで動かします。)

最初に次を読んでください(読むだけで、まだ何も変更しない)。

1. `docs/VALUE_VALIDATION.md`(**検証の記録と、事前登録の合格基準。最初に読む**)
1. `docs/VALUE_DESIGN.md`(設計。**特に §5 データの形式、§9 過去検証**)
2. `docs/INVESTOR_RESEARCH.md`(§0 調査の限界、§1 投資家別の記録)
3. `docs/VALUE_CATALYST_PLAN.md`(最初のたたき台。経緯の参考)
4. `README.md`、`docs/HANDOFF.md`(ニュース連想モデルのセットアップ。すでに済んでいれば再実行は不要)

---

## 0. 前提と守ること

- **クラウドからは外部のデータ元(EDINET、TDnet、Yahoo Finance、各ブログなど)に一度も接続できていません。** このモデルのコードは、合成データのテスト(クラウドでは256件)でしか動かしていません。**実データとの食い違いが必ずあります。これを見つけて直すのが最大の仕事です。**
- **ユーザーの既存システム(ファンダメンタルズ分析、需給分析、株価DB)は読み取り専用です。** 変更・上書き・削除は一切しない。
- `data\` と `config\config.yaml` は git に入れない(`.gitignore` 済み)。**財務データ、株価、開示の本文、API キー、個人情報をコミットしない。**
- 相手先に負荷をかけない。取得の間隔を守り、個人利用の範囲で使う。EDINET・TDnet の利用規約を確認する。
- **数値の閾値は検証前の仮置きです**(`src/assoc/value/thresholds.py`。「△」は出典が弱い)。**過去検証の結果を見てから閾値を調整するのは、過剰適合になりやすい。** 調整するなら、調整に使わなかった別の期間で再確認する。調整したら `docs/DECISIONS.md` に日付・内容・理由を追記する。
- **件数・結果は、推測で書かず、実際に実行して確かめたものだけを報告する。** 良い結果が出なくても、そのまま報告する(「型Aはベースラインと差がなかった」は正常で価値のある結果)。
- 変更は小さく分けてコミットし、**`claude/youthful-ride-lw1xks` ブランチ**に push する(クラウド側がそれを取り込む)。コミットメッセージは日本語でよい。
- 分からないこと、既存システムに影響しそうなことは、推測で進めずにユーザーに聞く。

## 1. 作業の順序

### フェーズA セットアップ(目安30分)

1. ブランチを取り込む:`git clone -b claude/youthful-ride-lw1xks https://github.com/chachichucheto/stock-analysis-system.git`(ニュース連想モデルで取り込み済みなら、`git fetch` と `git checkout claude/youthful-ride-lw1xks`)。既存システムとは別のフォルダに置く。
2. セットアップ:`powershell -ExecutionPolicy Bypass -File scripts\windows\setup.ps1`(済んでいれば `pip install -r requirements.txt` だけでよい)。
3. `.\.venv\Scripts\python.exe -m pytest -q`。**256件(以降の変更で増える)がすべて通ることを確認する。** 通らなければ原因を報告する(Windows 固有の問題の可能性)。
4. `config\config.yaml` に `value:` の節を足す(`config\config.example.yaml` の末尾を参照)。`capital_yen` は**ユーザーに総資金のおおよそを聞く**(株数の上限の計算に使う。0なら出さない)。

### フェーズB データの用意【最重要・最大の作業】

`docs/VALUE_DESIGN.md` §5 の形式で、`data\value\universe.csv` と `data\value\financials.csv` を作ります。**このモデルの信頼性は、ここの正確さでほぼ決まります。**

1. **株価DBの確認(読み取りのみ)**:
   - **上場廃止した銘柄の株価が残っているか**(生存者バイアスの防止に必須。残っていなければ、その旨と、取れる範囲を報告する)
   - TOPIX(または 1306)があるか、日足の列、株式分割の調整、更新時刻
   - 結果を `docs/S1_VALUE_REPORT.md` にまとめる(個人情報・キーは書かない)。
2. **銘柄マスタ `universe.csv`**:JPX の上場銘柄一覧(`master/universe.py` が取っている)に、**上場日・上場廃止日・東証33業種**を足す。**上場廃止銘柄とその廃止日の取得元**を探す(JPX の公表資料、EDINET のコード一覧など)。取れなければ、取れた範囲と、バイアスの大きさの見込みを報告する。
3. **財務データ `financials.csv`**:EDINET API の有価証券報告書・四半期報告書(XBRL)から、§5.2 の列を作る。
   - **`disclosed_date` は実際の開示日**(EDINET の提出日、または TDnet の開示日)。期末+固定日数で埋めない(先読みの原因になる)。
   - 損益は**直近12か月(TTM)**に直す(四半期は累計から計算:今期累計+前期通期−前期同期累計)。
   - 取れない項目は空にする(推測で埋めない)。**どの項目が何割取れたか**を報告する。
   - 最低でも直近5年分は欲しい(型Bの本決算5期、過去検証の期間のため)。
   - 取得処理は `src/assoc/value/` に追加してよい(例: `value/ingest_edinet.py`)。**解析部分(純関数)と取得部分を分け、小さな見本を `tests\fixtures\` に足してテストする**(`ingest/edinet.py` と同じ作法)。
4. **点検**:`.\.venv\Scripts\python.exe -m assoc value check`。エラーが0になるまで直す。警告は内容を報告する(特に、財務データが無い銘柄の数、欠損が多い項目)。

### フェーズC 過去検証と合格判定

**先に `docs/VALUE_VALIDATION.md` を読む**(特に §2 検定の作りと検出力、§5 事前登録の仮説と打ち切りの基準、§6 検証の順序)。判定の基準は、結果を見る前に固定されている。**結果を見てから基準や閾値を動かさない。**

**順1:価格だけの検証を先にやる(財務データが無くてもできる)。**
- 株価DB(上場廃止込み)だけで、型D(25日線乖離)を検証する。`financials.csv` が無い間は、`value backtest` の型A・B・Cが該当しないので、型Dの行(H4)だけを見る。
- そのために、先に `universe.csv`(上場日・上場廃止日・業種)だけは作る(フェーズBの2)。財務データの用意(フェーズBの3)は、この結果を見てからでもよい。

**順2:財務データがそろったら、型A・B・Cを検証する。**
1. **データの期間を2つに分ける**(例:前半2020〜2022、後半2023〜2025。取れる範囲で)。
2. 各期間で実行:`.\.venv\Scripts\python.exe -m assoc value backtest --start YYYY-MM-DD --end YYYY-MM-DD --require-delisted`
   - `--require-delisted` で、上場廃止銘柄が無いとエラーになる。**外した結果は、生存者バイアスの警告つきとして扱い、採用の根拠にしない。**
3. 結果(`data\reports\value_backtest_*.md`)を読み、**`VALUE_VALIDATION.md` §5.1 の主セル(H1〜H5)だけで判定**する。他のセルは探索であり、良く見えても採用の根拠にしない(28セルを見れば偶然 t>2 が出る)。
4. 警告(上場廃止の打ち切り、観測の欠け、基準日数不足)の内容と件数も報告する。**基準日数が足りないときは「差なし」ではなく「結論を出さない」と報告する。**
5. **結果が悪くても、閾値を調整して通そうとしない。** まず次を点検する:データの誤り(開示日、TTM の計算、単位)、型の条件が実データで1件も該当しない原因(`missing` の内訳)。そのうえで、調整案と理由をユーザーに報告して判断を仰ぐ。
6. §5.2 の打ち切りの基準に当たったら、運用に進まず、その旨を報告する(**辞めるのも正しい結果**)。
7. 通った型についてだけ、取引コスト(スプレッドと手数料の見積り)を入れた超過リターンを計算して報告する。

### フェーズD 開示読解の評価セットと、開示本文の取得

1. **開示の本文の取得**:パックの `disclosures[].body_excerpt` は今は空です。TDnet の開示(PDF/XBRL)から、**本文の要点部分(原文のまま)**を取り出して入れる処理を足す(`value/run.py` の `_disclosures` を拡張。取得は1銘柄あたり少数に絞り、間隔を守る)。要約はしない(引用の照合に原文が必要)。
2. **評価セット**:`knowledge/value_eval/README.md` の形式で、**本物の開示30件**を作る。
   - 正解は、開示後60営業日以内の実際の値動き(TOPIX 超過 +10% 以上=Medium 以上)で決める。**動かなかった開示を、動いたものと同数**入れる。
   - 作り話は入れない。開示の原文の取り扱い(私的利用の範囲)に注意し、リポジトリは非公開のままにする。
3. **評価の実行**:`/value-daily` と同じ手順で評価セットの各事例にプロンプトを適用して出力 JSON を作り、`python -m assoc value eval --file <出力>` で精度を測る。G3(重大な取り違え10%以下、引用の照合率100%)を確認する。
4. プロンプトのわかりにくい点・スキーマが厳しすぎる点は、**クラウド側に直してほしい点として報告する**(`prompts/value-disclosure-v1.md` を勝手に書き換えない。直したら版を上げて `value-disclosure-v2.md` とする)。

### フェーズE 予行演習と自動実行

合格した型(`VALUE_VALIDATION.md` §5.3)について、ユーザーと相談して進めます。

1. `/value-daily`(`.claude/commands/value-daily.md`)を1回、予行演習として実行する。つまずいた点を記録する。レポート(`data\reports\value_YYYY-MM-DD.md`)をユーザーに見せる。
2. **予行演習の記録は正式な記録ではない。** 正式な記録の開始は、ユーザーが「今日から本番」と言った日から。それまでの `data\records\value_*.jsonl` は、ユーザーに確認したうえで消してよい。
3. 毎日のスクリーンを自動実行に登録する:`powershell -ExecutionPolicy Bypass -File scripts\windows\register_tasks.ps1 -WithValue`(毎日18:30に `value screen`。株価DBの更新後であることを確認する)。
4. 開示読解(LLM の手順)は、ニュース連想の夜の手順と**同じ日にまとめて**行う運用を、ユーザーと相談する(作業時間は合計30分以内を目安)。

過去検証の結果は、`data\reports\value_backtest_*.md` の**表をそのまま貼る**(要約で良い結果に見せない)。

## 3. うまくいかないとき

- **型が1件も該当しない**:`python -m assoc value screen` のパックの `screened_hits` が0なら、足切り(`passes_base`)を通る銘柄の数を確認する。時価総額の計算(株式数の単位、自己株式)、売買代金の下限が原因のことが多い。
- **財務データの項目が取れない**:空のまま進める。その型が該当しにくくなるだけで、推測で埋めるより安全。取得率を報告する。
- **過去検証が遅い**:銘柄数 × 基準日数だけ株価を読む。基準日を減らす前に、株価の読み込みの重複(`run_backtest` のキャッシュ)を確認する。
- **既存システムの構造がよく分からない**:推測で触らず、ユーザーに聞く。
- **ブログ・記事の本文が読める環境なら**:`docs/INVESTOR_RESEARCH.md` §0 に挙げた一次資料を読み、△の項目(売却ルール、売却PER、リスク管理など)を確定して、閾値の出典を直す(クラウドの調査は検索要約だけだった)。
