## 1. 全体構成

### 1.1 処理の流れ

```
[夕方・自動]  Python
  1  収集          RSS・Google News・GDELT・Wikipedia閲覧数・TDnet・EDINET・上場銘柄一覧・株価
  2  イベント化    同じ出来事の記事をまとめ、イベント候補にする
  3  足切り        注目度・新規性・開示の種類で 0〜3件に絞る(進行中シナリオの関係分は別枠)
  4  株価の計算    騰落率・出来高倍率・普段の値動きの幅・TOPIX 超過
  5  入力パック    LLM に渡す材料を1つの JSON にまとめる

[夜・手動]  Claude Code(/association-daily)
  6  等級付け(暫定)   S/A/B/C
  7  シナリオの照合    既存シナリオの強化・弱体化・繰り返し・消滅、または新しいシナリオ
  8  シナリオを立てる  時間の型、起動・終了の条件、連想(2つの視点)、候補、想定上昇幅、
                      過去事例の参照、確認計画
  9  裏取り            上位1〜2件だけ。反証も調べる
  10 出力              スキーマに沿った JSON

[夜・自動]  Python(コマンドの最後に呼ぶ)
  11 確定              スキーマの検証、銘柄コードと社名の照合、信頼度の確認、時刻の付与、追記
  12 計算              鮮度・織り込み度・反応の診断・自信度・本命の判定・除外
  13 レポート          O1 連想レポート・O3 連携ファイル

[翌朝・自動]  米国市場の1段目の反応を確認し、閾値を超えたら通知する
[翌日の引け後・自動]
  14 等級の確定        1段目の反応で検算
  15 状態の更新        織り込み度・鮮度・終了判定・売りのサイン・「動いた」の判定

[月1回]  Python の集計 + Claude Code(/association-monthly)
  16 振り返り          O2 振り返りレポート(見逃し・外れ・3つの指標・改善の実行)
```

### 1.2 担当の分け方

- **Python**:事実と数字を扱う(収集、計算、時刻、照合、確定、集計)。
- **LLM**:発想と解釈を扱う(等級、連想、確認計画、裏取りの要約、反証)。
- LLM が出した数値(想定上昇幅、実現確度など)は「推定値」として記録する。**時刻と株価に基づく数値は、必ず Python が計算する。**

## 2. 不変条件(全体に共通する決まり)

1. **いつ知り得たかを記録する**:すべての記録に `first_observed_at`(本システムが最初に取得した時刻)を持たせる。判断に使ってよいのは、その判断の時点までに取得済みの情報だけとする。ソース側の公開時刻(`published_at`)は後から書き換わることがあるので、判定には使わない。
2. **時刻は UTC で保存する**:表示だけ日本時間にする。営業日の判定は、東証の営業日カレンダー(既存システムにあれば再利用)で行う。鮮度や想定期間は営業日で数える。
3. **追記だけで記録する**:シナリオ・候補・ランキング・裏取りの記録は書き換えない。変えるときは新しい版を追記する。
4. **落としたものも記録する**:足切りで落としたイベント、C級・B級の判定、候補にしなかった銘柄も理由とともに残す。
5. **LLM の推論は証拠にしない**:証拠は URL・取得時刻・値・信頼度がそろったものだけとする。
6. **使ったモデルと指示文の版を記録する**:実行ごとに `model_id` と `prompt_version` を残す。
7. **既存資産を壊さない**:既存システムのコードとデータ(yfinance の株価DBを含む)は読み取り専用で使う。
8. **件数は推測しない**:報告に書く件数は、すべて機械的な集計による。
9. **過去事例と実運用の記録を分ける**:過去事例ライブラリ(学習用)と、実運用の予測の記録(能力の測定用)は別に保存する。過去事例を LLM に解かせた結果は、能力の測定に使わない。

## 4. 保存の方針

- **git で管理するもの**:コード、設定、指示文、スキーマ、文書、テーマ一覧、前提カード、過去事例ライブラリ(小さな JSON・Markdown)。
- **git に入れないもの**:生データ、DB、レポート(`data/` に置き、`.gitignore` で除外する)。
- 生データ以外は、スクリプトで作り直せるようにする。
- **作り直せない記録**(予測の記録、裏取りの記録、実行の記録)は追記専用の JSONL とし、1行ごとにハッシュを付ける。これだけは git 以外の場所にも毎日複製する(バックアップ)。
- DB は DuckDB(1ファイルで高速に集計できる)。
- ニュースの本文は保存しない(容量と著作権のため)。

## 6. 処理の詳細

### 6.1 収集(Python・自動)

- 各ソースを所定の頻度で取得し、`first_observed_at` を付けて保存する。
- 取得に失敗した場合は記録し、次回に再試行する。3回続けて失敗したら、レポートの冒頭に警告を出す。
- **LLM の夜の手順を実行しなかった日も、収集は続ける。**

### 6.2 イベント化と足切り(Python・自動)

1. 見出しと固有表現の類似度で、同じ出来事の記事を1つのイベントにまとめる。
2. 次のどれかを満たすイベントを通す(閾値は §7)。
   - 注目度(媒体数・GDELT・Wikipedia)が、過去90日のイベントの上位5%
   - 注目度が急に伸びている(前日比の伸びが上位5%)
   - 株価への影響が大きい種類の開示(大量保有報告書、TOB、大手との資本業務提携、業績予想の大幅な修正、国の大型予算・規制の決定)
3. **新規性**:すでに記録した事実と同じ内容(`novelty_hash` が一致)は落とす。
4. 通ったものから注目度の順に**最大3件**を LLM に渡す。進行中のシナリオの対象企業やキーワードに一致するものは、上限の枠外で渡す。
5. 落としたイベントも、理由とともに記録する。

### 6.3 入力パック(Python・自動)

LLM に渡す JSON には、次をまとめる。

- 足切りを通ったイベント(見出し、要約、URL、注目度、開示の種類)
- 関係するテーマの前提カード(最新版)と温度
- 進行中・待機中のシナリオの一覧(最大15件)と、それぞれの確認計画の状況
- 関係しそうな過去事例(テーマと時間の型で検索したもの)
- 候補になり得る銘柄の株価の状態(1段目の反応、出来高、普段の値動きの幅)
- 今日が公表日の統計(確認計画の「次の公表」に当たるもの)

### 6.4 夜の手順(Claude Code・手動)

`/association-daily` として固定する。指示文は `prompts/` で版を管理する。

1. **暫定の等級**:各イベントに S/A/B/C を付ける。4つの質問のうち1〜3に答え、前提カードの数字と新しい数字を並べて示す。
   - 前提カードがないテーマで S・A級の可能性があるときは、**ニュースを見る前の市場の想定を先に書き出して前提カード v1 を作り**、それを基準に等級を付ける。
   - 翌日の検算に使う1段目の銘柄を指定する。1段目に上場企業がない場合(政策・災害など)は、テーマ関連の銘柄群または業種指数を指定する。
2. **シナリオの照合**:進行中・待機中のシナリオそれぞれについて、強化・弱体化・繰り返し・消滅のどれに当たるかを判定する。強化と弱体化の両方の読み方を書いたうえで判定する。
3. **新しいシナリオ**(S・A級のみ):
   - 時間の型、起動条件、終了条件、想定期間(局面展開型は `THEMES.md` のひな形を初期値にする)
   - 連想:経済的なつながりと投資家の連想の2つの視点で、1段目と2段目以降の候補を出す(1シナリオ最大5銘柄。銘柄コードと社名の両方を必須とする)
   - 想定上昇幅(下限・中央・上限)とその根拠
   - 似た過去事例(ライブラリから引く)
   - 確認計画(矢印ごとに、指標・情報源・基準・次の公表日)
   - どのテーマにも当てはまらなければ、新テーマ候補の目印を付ける
4. **裏取り**:その夜の対象は、新しく立てたシナリオと強化されたシナリオのうち、上位1〜2件だけとする。上位の決め方は、S級を優先し、次に裏取り前の推定値(実現確度 × 想定上昇幅の中央値)の大きい順とする。Web 検索で確認計画の矢印を確かめ、反証も調べる。証拠は URL・値・信頼度とともに出力する。
5. **出力**:スキーマに沿った JSON を `data/inbox/` に書き出し、確定処理を呼ぶ。

**最小手順(10分)**:時間がない日は、2(照合)と、注目度が最大の1件の等級付けだけを行う。

### 6.5 確定(Python・自動)

- JSON スキーマで検証する。不合格なら確定せず、理由を表示する。
- **銘柄コードと社名を、銘柄マスタと別名辞書で照合する。** どちらかが合わない候補は確定しない。取り違えの件数も記録する。
- 証拠の URL がない、または信頼度3・4の証拠だけで「確認」とされた矢印は、「未確認」に直す。
- 時刻・モデル・指示文の版を付け、追記する。

### 6.6 計算(Python・自動)

| 項目 | 計算方法 |
|---|---|
| 鮮度 | 起動日からの営業日数 ÷ 想定期間 で減らす(100% → 0%)。待機中は止める。強化された日を新しい起点とする |
| 織り込み度 | 起動日の前日終値からの TOPIX 超過上昇 ÷ 想定上昇幅(中央値)。想定上昇幅の版番号も記録する |
| 反応の診断 | §6.6.1 の規則で1つのラベルにする |
| 自信度 | 実現確度 × 残り余地 × 鮮度の補正(`CONCEPT.md` §8.4) |
| 本命 | 自信度の上位3件。ただし §8 の除外条件に当たるものは本命にしない |
| ★ | 自信度を §7 の固定の閾値で4段階に分ける |

#### 6.6.1 反応の診断のラベル

「注目度」はイベントの注目度、「1段目の反応」は1段目の銘柄の反応、「候補の反応」は候補銘柄自身の反応を指す(判定の閾値は §7)。上から順に当てはめ、最初に当たったものをラベルとする。

| 順 | 条件 | ラベル |
|---|---|---|
| 1 | 候補が反応した(織り込み度80%未満) | 織り込み進行 |
| 2 | 1段目が反応した、候補は反応していない | **時間差あり** |
| 3 | 1段目・候補とも反応していない、注目度が高い | ⚠ 無視されている疑い |
| 4 | 1段目・候補とも反応していない、注目度が低い | 未発見 |
| 5 | 注目度が低いのに候補が反応した | 早耳の先回り(1より優先して表示する) |

1段目に上場企業がない場合は、§6.4 で指定した銘柄群または業種指数を1段目とみなす。

### 6.7 レポート(Python・自動)

- **O1 連想レポート**:`CONCEPT.md` §9.1 の構成で、Markdown と HTML を出力する。
- **O3 連携ファイル**:`data/export/picks_YYYYMMDD.csv`。列は日付、銘柄コード、社名、シナリオ番号、自信度、崩れる条件。

### 6.8 翌朝と翌日の自動処理(Python)

- **翌朝**:その夜のシナリオで1段目に米国企業がある場合、米国市場の終値の動きを確認する。普段の値動きの2倍を超えていれば、通知を出す。
- **翌日の引け後**:
  - **等級の確定**:1段目の銘柄(または指定した銘柄群・業種指数)の TOPIX 超過が(ザラ場中のニュースは当日、引け後のニュースは翌営業日に反応するので、その2日のうち大きいほうで)、普段の値動き(20日の標準偏差)の何倍かを計算する。§7 の閾値で、暫定の等級を確定・修正する。見落としの可能性があれば、翌日のレポートに出す。1段目を指定できなかった場合は、暫定の等級をそのまま確定とし、「検算なし」の印を付ける。
  - **状態の更新**:織り込み度、鮮度、終了の判定(`CONCEPT.md` §8.3)、起動条件の判定材料の提示。
  - **売りのサイン**:過去に本命とした銘柄について、§8.3 の4つを検出する。
  - **「動いた」の判定**:`pick_tracking` を更新する(§7)。

### 6.9 月次の振り返り(Python の集計 + Claude Code)

1. **Python の集計**:
   - 的中率:銘柄単位(本命のうち「動いた」割合)とシナリオ単位(本命のうち1銘柄でも動いたシナリオの割合)の両方を出す。偶然の場合(同じ期間に全銘柄の中で「動いた」銘柄の割合を、`universe_daily` と株価から計算)と比べる。
   - 先行性:最初に挙げた日と「動き出した日」の差。
   - 1段目だけを挙げた場合の的中率・先行性。
   - **見逃しの候補の抽出**:その月の S・A級のイベントごとに、その後20営業日で「動いた」銘柄を全銘柄から抽出する。
   - 運用の状況(`run_log` から)。
2. **Claude Code(`/association-monthly`)**:
   - 見逃しの候補のうち、イベントと関係があるものを判定する(事後の判定として記録する)。これで捕捉率を出す。
   - 見逃しと外れの原因を分類し、直す先(指示文、前提カード、等級の基準、過去事例)を提案する。
   - 月内の大きなイベントを過去事例ライブラリに追加する。
3. 改善を反映したときは、指示文の版を上げ、日付と理由を `DECISIONS.md` に追記する。

### 6.10 過去事例ライブラリ

- **最初の登録(S2)**:大地震、感染症、戦争、政策の大転換、大型の技術ニュースなど、`THEMES.md` のテーマに関係する過去の大きな出来事から、30件程度を選ぶ。

### 6.11 テーマの温度と前提カード

- **温度**:当面は、週1回 LLM が「上昇中/横ばい/冷却中」の3段階で更新する。材料は、その週のテーマ関連のニュースの数と、テーマ関連銘柄の値動き。

## 15. ローカル化後の追加設計(2026-10-01。DECISIONS D34)

### 15.1 株価:既存システムのファイルを読み取り専用で重ねる(`market/layered_prices.py`)
- 前提(2026-09-30 に既存側を読み取りで確認):既存の全銘柄日足 `cis_engine/data/raw/daily_ohlcv.parquet` は 2004-07〜**2026-07-24 で更新停止**。日次で更新されているのは `tactical_universe_ohlcv.parquet`(555銘柄、6/2〜)だけ。**7/25以降の全銘柄は誰も取得していない**。
- 2つの既存ファイルは、重なる期間で終値が食い違う(555銘柄中185銘柄。分割調整の違い)。7082 のように壊れた値もある。
- 層(新しい順):既存・日次555銘柄 → 連想側・空白補完(`data/prices_gap/`、yfinance を調整なしで取得) → 既存・全銘柄履歴。
- **つなぎ目の補正**:重なった日の終値の比(中央値)で古い側の倍率をそろえる。比が安定しない(最大/最小>1.10)、または重なりが無くつなぎ目の変化が35%超なら、古い側は使わず警告する。
- **品質ゲート**:株価が500万円超・0以下・欠損の行を捨てる。
- **古い株価は「今の株価」として返さない**:直近の評価で最新日が10日以上前なら、その銘柄だけ自動補完し、それでも古ければ「データなし」(呼び出し側で除外)。
- `assoc prices status`(鮮度の確認)/ `assoc prices fill [--codes|--all]`(補完)。日本語パスの仮想環境で yfinance が SSL エラーになる問題は `netfix.py` が自動で対処する(証明書を ASCII パスへコピー)。

### 15.2 足切り:開示を別枠にする(`events/gate.py`)
- ニュースは注目度(媒体数)の順に最大3件、**開示(TDnet・EDINET)は別枠で最大3件**(`gate_max_disclosure_events`)。開示は種類の優先度(TOB > 提携 > 業績予想の修正 > 大量保有)→注目度の順(暫定)。
- 媒体数は「媒体名」で数える(`events/cluster.py: media_of`。NHK の4フィードは1媒体、Google News は実際の媒体名)。

### 15.3 入力パックの追加項目(`pack/build.py`)
- `events[].media`(報じた媒体名)、`events[].urls`(直接開ける URL を先頭に。Google News の中継 URL は後ろ)
- `watch`:候補ウォッチの結果(§15.4)
- `health`:継続性チェックで「注意」「劣化」になった・状態が変わった銘柄(§15.5)

### 15.4 候補ウォッチ(`watch.py`、`assoc watch`)
本命と進行中シナリオの候補だけを対象に、前回の点検以降の新しい材料(その銘柄の開示・見出しに社名/コードを含むニュース・7日以内の決算)を Python で数える。**トークンは使わない**。`new_material=true` の銘柄だけを夜の深掘りの対象にする(材料が無い銘柄は調べ直さない)。夜の検索の予算は、新シナリオの裏取り15回・ウォッチ/ヘルスの銘柄10回・予備5回(`prompts/daily-v1.md` 手順2.5)。

### 15.5 継続性チェック(`tracking/health.py`、`nextday` で毎日)
選んだ銘柄の期待が「続いているか」を、Python だけで毎日判定し `health_snapshot`(追記専用)に記録する。売りのサイン(出口の合図)より手前の「期待の健康状態」。
- 見る項目:TOPIX 超過の維持・直近5日の向き・ピークからの押し戻し/売買代金(5日÷20日)/新しい材料の有無/悪材料の語を含む見出し(要確認の目印)/停滞(期間の4割経過で織り込み・材料とも止まる)/シナリオの弱体化・終了
- 状態(優先順):終了 > 劣化 > 織り込み進行 > 注意 > 継続
- 閾値は暫定(`config.Thresholds.health_*`)。**記録を積んで、「劣化」判定が実際の失敗を先に示していたかを検証する**(検証前は判断の補助であり、評価指標には入れない)。
- 起動前(待機)のシナリオは対象外。本命にしてから60営業日で追跡を終える。

### 15.6 共有棚(`shared_export.py`、`assoc export`)

## 付録A. 旧版(v0.3)からの主な変更

| 旧版 | v1.0 | 理由 |
|---|---|---|
| 売買成績の評価(手数料、ストップ高の約定、出口の比較) | 削除 | ゴールを「探す能力」に再定義した |
| 対照群4種類、単純な方法5種類との比較 | 「偶然の的中率」と「1段目だけの場合」の2つに絞った | どちらも記録から後で計算でき、毎日の記録が不要 |
| 検証の問い20個 | 3つの指標(的中率・捕捉率・先行性)と見逃しの分析 | 改善に直結するものに絞った |
| 事例集は後回し・発見用に限定 | 過去事例ライブラリを中核に格上げ | 過去の反応は投資家の連想の元ネタそのもの |
| 毎日の裏取り | 新しい情報が出たときだけ | 作業時間の削減。何も起きていなければ調べる必要はない |
| テーマの5段階(誕生〜冷却) | 新テーマ候補の目印だけ | 新しいテーマの誕生はまれ。大半は既存テーマ × サプライズ |
| 保有銘柄の入力 | 不要。過去に本命とした銘柄に売りのサインを出す | 入力の手間なく、売るべきニュースに対応できる |
| 有効期限を日数で一律に決める | 時間の型と起動・終了の条件 | 賞味期限は事例によって違う |
| 格付け A/B/C | 本命・監視と除外条件 | 自信度ランキングに一本化した |
| 週1回の簡易な答え合わせ | 月1回の振り返りのみ | 件数が少ない時期の早まった判断を避ける |
