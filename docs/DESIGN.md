## 1. 目的と前提条件

### 1.1 目的

日々のニュースから「連想ゲーム」で**まだ株価に十分織り込まれていない銘柄**を見つけ、スイング候補として毎日提示する。

最終的に確かめたいのは次の問いである。

> **ニュース連想には、将来リターンを予測する情報価値があるか。あるなら、どの型の連想に、どの条件で存在するか。**

「ニュースと関連銘柄の検索システム」は作らない。

### 1.2 確定済みの前提

| 項目 | 決定 |
|---|---|
| 時間軸 | **スイング**(数日〜数週間)。主な評価期間は 5 / 10 / 20 営業日 |
| 出力 | **候補の提示まで**。売買シグナル・発注は作らない |
| データ | **無料ソースのみ** |
| 株価 | **yfinance**(ローカルで取得・日次更新済みの既存データを再利用) |
| LLM | **Claude Code を手動実行**(API自動化はしない) |
| 実行環境 | **最終的にローカル中心**。成果物は git で受け渡す |

### 1.3 中心仮説

1. **市場が乗る連想と経済的に正しい連想は別物である。** 儲けの源泉は前者。ただし後者の裏付けがない連想は崩れやすい。
2. **ニュースの大きさが重要である。** 日本中・世界中が騒ぐニュースほど、株価は素直に、長く反応する。
3. **スイングの狙い目は、注目度が加速している途中の2段目の連想である。** 1段目は即座に織り込まれ、3段目以降はノイズが多く市場も追いつかない。
4. **注目度のピークアウトは出口の目安になる。**
5. **同じ仮説が新しい事実で段階的に強化されていくとき、市場の反応も段階的に強まる。** どの段階で入るのが最も良いかは未知である(§7.5)。
6. **量より質。** すべてのニュースに反応しても成績は上がらない。本当に強いニュースと、上がる確度の高い少数の銘柄に絞るほど、成績は良くなる(§6.4・§7.6)。

これらは**仮説**であり、§10 の検証を通るまで前提として扱わない。

## 2. ChatGPT案の採否

ChatGPT案は検証の規律が非常に良い。一方で、個人・無料データ・手動LLMの制約に対して規模が大きすぎる。また、決定的な落とし穴が2つ抜けている。

### 2.1 採用する(本設計の骨格にする)

| 項目 | 本設計での扱い |
|---|---|
| Point-in-Time の徹底 | §4 の不変条件1。全レコードに時刻4種を持たせる |
| 事後分析と予測の完全分離 | §4 の不変条件2。データ構造もディレクトリも分ける |
| 勝ち銘柄だけの分析の禁止・対照群 | §9.3。対照群は予測時に**自動で**確保する |
| LLMの推論と証拠の分離 | §4 の不変条件3。証拠は一次情報のURLと時刻を持つものに限る |
| スコアを作っただけで有効と言わない | §8。特徴量を独立に保存し、重みは後で決める |
| 経済グラフと投資家連想グラフの分離 | §7.2。中心仮説1をそのまま構造にしたもの |
| 反証の生成(Red Team) | §7.4 |
| 予測スナップショットの不変性・版管理 | §9.1。追記のみで、書き換えは禁止 |
| 報告形式(9項目) | §13 |
| 既存モデル・既存データを変更しない | §4 の不変条件6 |

### 2.2 修正して採用する

| ChatGPT案 | 修正 | 理由 |
|---|---|---|
| 16段のパイプラインと13フェーズ | **6フェーズ**に圧縮(§12) | 個人開発で13フェーズは完走できない。段を分けても、手動のLLMセッション1回でまとめて処理する段が多い |
| 評価期間 1D〜252D | 主は **5 / 10 / 20D**、補助で 1 / 3 / 60D。120 / 252D は算出だけする | スイングなので、長期は主評価にしない |
| 10倍株の捕捉を重視 | 副次指標に格下げ | スイングの目的は初動の数週間。大化けは「取れたら嬉しい」扱い |
| 市場の認知は株価・出来高・SNS・アナリスト | **ニュースの大きさ(注目度)を独立の軸**として新設(§6) | 中心仮説2。ChatGPT案には「ニュース自体がどれだけ大きいか」の軸がない |
| SNSを収集する | **X は対象外**。Wikipedia閲覧数・GDELT・Googleトレンドで代替 | X API は有料 |
| 過去イベントのデータセットを先に作る | 事例集は**発見用**に限定し、**有効性の検証は前向き(フォワード)のみ**(§10) | 下記の落とし穴1 |

### 2.3 ChatGPT案に欠けていた落とし穴

**落とし穴1: LLM自身が未来を知っている。**
ChatGPT案はデータの時点管理(Point-in-Time)を徹底している。しかし、**連想を生成するLLM自体が、学習データを通じて過去の結末を知っている**。2020年のニュースを渡して連想させれば、LLMは「その後マスク関連が上がった」ことを知ったうえで答える。データの時刻をいくら厳密にしても、この漏れは防げない。
→ **有効性の検証に使えるのは、LLMの知識カットオフより後の、前向きに記録した予測だけ**とする。過去事例は仮説を作る材料にとどめる。

**落とし穴2: 無料データは過去分が消える。**
TDnet の公開閲覧は**約1か月分**しか残らない。NHK の RSS や Google News の RSS も直近分だけである。過去のニュースを後から無料で揃えることは実質できない。
→ **収集の開始そのものが最優先タスク**(フェーズ0)。モデルが未完成でも、生データの蓄積は今日から始める。1日遅れるごとに検証データが1日減る。

**補足: 同じイベントから出た候補は独立ではない。**
1つのイベントから候補が5銘柄出れば、それらの結果は強く相関する。候補の件数で統計を取ると過大評価になる。
→ 有意性の判断は**イベント単位**で集計する(§10.3)。

## 3. 全体アーキテクチャ

### 3.1 処理の流れ

```
[A] 決定的処理(Python・スケジューラで自動)
  ① 収集 ─ RSS / GDELT / TDnet / EDINET / Wikipedia閲覧数 / yfinance
  ② 注目度の計測 ─ 広がり・関心・国際性・持続・加速
  ③ 銘柄状態の計測 ─ 騰落率・出来高倍率・相対強度・地合い など
  ③' 【関門1】イベントの足切り ─ 注目度・新規性・型で選別し、LLMに渡すのは1日最大3件(§6.4)
  ③'' 単純な方法の候補の記録 ─ 比較用(§9.5)
  ④ 日次入力パックの生成 ─ 関門1を通ったイベント、銘柄状態、進行中の仮説、予定イベントをまとめたJSON

[B] LLM処理(Claude Code・手動で1日1回)
  ⑤ イベントの構造化 ─ ニュース群を Event にまとめる
  ⑤' 仮説の照合 ─ 各イベントが進行中の仮説を 強化/弱体化/無関係 のどれに当たるか、または新しい仮説かを判定(§7.5)
  ⑥ 連想の展開 ─ 経済グラフと投資家連想グラフ(分離)
  ⑦ 証拠の照合 ─ 企業資料との突き合わせ・証拠の強さ
  ⑧ 反証(Red Team) ─ 反対のシナリオを生成
  ⑨ 出力 ─ スキーマに合ったJSON(候補・連想経路・論拠・反論・上昇/警戒の方向)

[A'] 決定的処理(Python)
  ⑩ 検証してスナップショットに確定 ─ スキーマ検証、銘柄コードと社名の照合、時刻の付与、ハッシュ化、追記のみ
  ⑩' 【関門2】候補の格付け ─ 本命(A)/監視(B)/記録のみ(C)に振り分け(§7.6)
  ⑪ 対照群の自動抽出
  ⑪' 仮説の状態の更新 ─ 段階の追記、一定期間更新のない仮説の休眠化
  ⑫ 日次レポートの生成(Markdown/HTML。進行中の仮説と段階の推移を含む)
  ⑬ 結果の追跡 ─ 過去の予測の 1〜60D リターンを約定可能性込みで毎日更新
  ⑭ 実行記録 ─ 実行の有無・所要時間・見送り理由(§11.2)
```

**設計の要点:** LLMが担当するのは ⑤〜⑨(⑤' を含む)だけにする。時刻の付与、確定、評価は必ず Python で行い、LLMに書かせない。LLMは時刻や数値を誤ることがあるうえ、手動実行ではいつ実行したかも揺れるためである。

### 3.2 既存システムとの役割分担

| 層 | 役割 | 担当 |
|---|---|---|
| 仮説の生成 | 何が上がりそうか | **本モデル** |
| 確認・タイミング | 実際に資金が入り始めたか | 既存の需給システム |
| 安全弁 | 乗ってはいけない銘柄の除外、下値の目安 | 既存のファンダシステム |

連携は**ファイルの受け渡しだけ**で行う。本モデルが候補の銘柄コードをCSVに出し、既存システムがそれを読む。既存システムのコードは変更しない。連携を実装するのはフェーズ5で、それまでは参照にとどめる。

## 4. 不変条件(全フェーズ共通)

1. **Point-in-Time**:予測時点より後に公開された情報を使わない。全レコードに次の4つの時刻を持たせる。
   - `published_at`:ソース上の公開時刻
   - `first_observed_at`:本システムが最初に取得した時刻
   - `information_cutoff`:その予測が参照してよい情報の上限時刻
   - `prediction_at`:予測を確定した時刻
   - 予測に使ってよいのは `first_observed_at <= information_cutoff` の情報に限る。`published_at` は遡って書き換わることがあるため、判定には使わない。
2. **事後分析と予測の分離**:`expost/` と `predictions/` はディレクトリもスキーマも分ける。予測生成のコードは `expost/` を読めない構造にする(import しない、パスを渡さない)。
3. **LLMの推論は証拠ではない**:`evidence` として登録できるのは、URL、取得時刻、引用箇所を持つ一次情報(開示資料・有価証券報告書・報道)に限る。LLMの推論は `rationale` として別に持つ。
4. **スナップショットは追記のみ**:確定した予測は書き換えない。判断を変えるときは新しい版(`version+1`)を追記する。
5. **勝ち銘柄だけを学習しない**:候補になった全銘柄と、対照群の結果を保存する。
6. **既存資産を壊さない**:既存モデルのコード、既存データ(yfinanceの株価DBを含む)は読み取り専用で使う。
7. **件数は推測しない**:報告に書く件数はすべて機械的な集計による。
8. **時刻は UTC で保存する**:表示だけ日本時間(JST)にする。GDELT は UTC、国内ニュースは JST で、混ぜると日付がずれる。営業日の判定は JST の東証カレンダーで行う。
9. **ふるいも記録する**:関門1・2で落としたイベントと候補も、理由とともに記録する。ふるい自体が検証対象の仮説だからである。

## 5. データ層

### 5.1 無料ソースの一覧

| 用途 | ソース | 過去分の取得 | 注意点 |
|---|---|---|---|
| 国内ニュース | NHK・主要紙のRSS | 不可(直近のみ) | 本文は保存せず、見出し・URL・要約だけを保存 |
| 横断検索・広がり | Google News RSS(キーワード指定) | 不可(直近のみ) | 媒体数を数える用途 |
| 世界のニュース量 | **GDELT** | **可(2015年〜)** | API不要・無料。過去事例の注目度を後から再現できる唯一の手段 |
| 一般の関心 | **Wikipedia閲覧数API**(日本語版・英語版) | **可(2015年7月〜)** | 公式で安定。関心の主指標 |
| 検索の関心 | Googleトレンド | 可 | 非公式ライブラリ頼みで不安定なため、補助扱い |
| 適時開示 | TDnet 公開閲覧 | **約1か月で消える** | 日次収集が必須 |
| 大量保有・有報 | EDINET API | 可(一定期間) | APIキーの登録が必要。アクティビストの動き、取引先、大株主、セグメント |
| 株価・出来高 | yfinance(既存のローカルDB) | 可 | 既存の日次更新を再利用する。本モデルからは読み取りのみ |
| 信用残 | 既存の需給システムのデータ | 要監査 | フェーズ0で所在を確認する |
| テーマ分類 | 株探のテーマページなど | 一部 | 利用規約を確認のうえ、低頻度・個人利用に限定 |
| 予定イベント | 日銀会合・選挙・政策の施行日・決算発表予定・大型催事の日程(各公式サイト) | 可 | 先回り型の連想に使う(§7.3 `scheduled_event`) |
| 上場銘柄一覧 | JPX の上場銘柄一覧 | 不可(現在分のみ) | **毎日保存して、その時点の対象銘柄を記録する**(§5.4) |

### 5.2 保存方針(今回の引き継ぎ断念の反省)

- **git で管理するのは、コード・設定・プロンプト・スキーマ・設計書・事例集(小さなMarkdown/JSON)だけ**にする。
- 生データとDBは `data/` に置き、`.gitignore` で除外する。
- **生データ以外はすべてスクリプトで再生成できる**ようにする。ただし予測スナップショットは再生成できない(時点の記録そのものが価値のため)。これだけは別途バックアップする(§11.3)。
- ニュース本文は保存しない。容量と著作権の両面で、見出し・URL・要約・固有表現だけにする。
- DB は **DuckDB**(1ファイル・高速集計)。スナップショットは **追記専用の JSONL** とし、1行ごとにハッシュを付けて改ざんを検知できるようにする。

### 5.4 対象銘柄とデータ品質

- **その時点の上場銘柄で判断する**:JPX の上場銘柄一覧を毎日保存し(`universe_daily`)、対照群はその日の一覧から選ぶ。後から「今も上場している銘柄」だけで選ぶと、上場廃止した銘柄が抜け落ち、成績が良く見える(生存者バイアス)。
- **上場廃止した銘柄の結果も残す**:yfinance は上場廃止後にデータが消えることがある。予測・対照に使った銘柄の株価は、本モデルの DB に日次で複製して保持する。
- **株価の品質チェック**:株式分割の調整漏れ、欠損日、前日比の異常な飛び(例:±50%超で出来高の裏付けがないもの)を毎日機械的に検出し、該当する結果には印を付ける。
- **流動性の下限**:20日平均の売買代金が下限(未決 §15)に満たない銘柄は、候補になっても本命(A)にしない。スイングで実際に売買できない銘柄を本命にしても意味がないためである。

### 5.5 銘柄マスタと別名辞書(LLMの取り違え対策)

- 銘柄マスタ:銘柄コード、正式社名、市場、東証33業種、時価総額の帯。JPX の一覧と既存のファンダシステムから作る。
- **別名辞書**:ブランド名・略称・旧社名・英字名 → 銘柄コード(例:ユニクロ → 9983 ファーストリテイリング)。運用しながら追記する。
- **LLMの出力は、銘柄コードと社名の両方を必須とする。** Python がマスタと照合し、どちらかが合わなければ確定させずに差し戻す。取り違えの発生率自体も記録する(LLMの信頼性の指標)。
- LLMが主張した取引関係・資本関係のうち、証拠のURLが付いていないものには `unverified` の印を付ける。

## 6. ニュースの大きさ(注目度)の計測

中心仮説2と3を検証するための、本設計の独自の軸である。

### 6.1 4つの指標

| 指標 | 定義 | ソース |
|---|---|---|
| 広がり | 24時間以内に報じた媒体の数 | Google News RSS、GDELT(国内) |
| 関心 | 関連するWikipedia記事の閲覧数(平常時比) | Wikipedia 日本語版 |
| 国際性 | 海外での報道量・関心 | GDELT(全世界)、Wikipedia 英語版 |
| 持続・加速 | 継続日数と、上の3指標の日次の傾き | 上の日次推移から算出 |

イベントに対応するWikipediaの記事やGDELTの検索語は、⑤のイベント構造化でLLMに提案させる。**提案した語は Event に保存し、以後は固定する。** 後から語を変えると、注目度の推移が別物になるためである。

### 6.2 注目度の局面ラベル

```
Rising(加速中) / Peak(ピーク付近) / Fading(減衰) / Flat(話題化せず)
```

- 入口の仮説:Rising のイベントの2段目の候補が最も良い。
- 出口の仮説:イベントが Fading に入ったら、関連候補の優位性は消える。

どちらも仮説であり、ラベルの有効性そのものを §10 で検証する。

### 6.3 過去事例への適用

GDELT と Wikipedia は2015年以降の過去分を取れる。このため、**過去事例の注目度の推移は後から再現できる。** 事例集(§9.4)では、各事例の注目度の曲線と株価の反応を並べて保存する。

### 6.4 【関門1】イベントの足切り(量より質・その1)

すべてのニュースに連想をかけると、候補が際限なく増える。その結果、質が落ち、毎晩の手動作業も続かなくなる。そこで、**LLMに渡す前に Python で機械的に絞る。**

#### 全体の絞り込み(目安)

```
ニュース   数百〜数千件/日
  ↓ 重複統合(同じ出来事の記事をまとめる)
イベント候補   数十件/日
  ↓ 関門1(本節・Python)
LLMに渡すイベント   0〜3件/日   ← 進行中の仮説の更新確認は別枠
  ↓ 連想(1イベントあたり候補は最大5銘柄)
候補   0〜15件/日
  ↓ 関門2(§7.6)
本命(A)   0〜3件/日   ← 「今日は該当なし」を正常な結果とする
```

#### 通過条件(いずれか。閾値は暫定で、§10.4 で事前に固定する)

1. **大きさ**:注目度の総合値が、過去90日のイベント分布で上位5%以内
2. **加速**:注目度の加速度が上位5%以内で、`Rising` 局面にある(まだ小さいが急拡大中)
3. **強い型の一次情報**:TDnet・EDINET のうち、株価への影響が大きい型(大量保有報告書、TOB、大手との資本業務提携、国の大型予算・規制の決定 など)
4. **進行中の仮説の強化候補**:進行中の仮説の対象企業・キーワードに一致するもの(上限3件の枠外)

加えて、**新規性の条件**を課す。既知の事実の繰り返しにすぎないイベントは通さない(§7.5 と同じ重複判定)。

#### ふるいの漏れの検査

関門1で落としたイベントに、実は大相場の種が混じっている可能性がある。そこで、**落としたイベントから週1件を無作為に選び、LLMで同じ処理を行って記録する**(`gate_audit`)。その候補の結果が、通過したイベントの候補と同等以上なら、関門1の閾値が厳しすぎるということになる。

## 7. LLMワークフロー(Claude Code・手動)

### 7.1 実行の形

- Claude Code のカスタムコマンド(例: `/association-daily`)として固定する。プロンプトは `prompts/` で版管理し、`prompt_version` をスナップショットに記録する。
- 入力は ④ の日次入力パック(JSON)**だけ**とする。セッション中の Web 検索は、証拠の照合(⑦)のときに限り許可する。その場合も、取得したURLと時刻を証拠として記録する。
- 出力は JSON スキーマに従う。Python 側で検証し、不合格なら確定させない。
- **ばらつきの測定**:週1回、過去の入力パックを新しいセッションで再実行し、候補の重なり具合(一致率)を記録する。一致率が低い型の連想は、再現性がないものとして扱う。
- **モデルの更新**:Claude Code のモデルが変わった日は `run_log` に記録し、分析上の区切りとする。更新の前後の成績を混ぜて評価しない。
- **実行時刻の推奨:夜(20時以降)を主とする。** 引け後の TDnet 開示と、国内の夕方のニュースを取り込めるためである。翌朝の寄り前に、米国市場とその夜のニュースの差分だけ確認する任意の手順を用意する。

### 7.2 2つのグラフを分ける

| | 経済グラフ | 投資家連想グラフ |
|---|---|---|
| 問い | 実際に利益に効くか | 投資家はこのニュースで何を思い浮かべるか |
| 経路の例 | 原料価格↓ → 原価↓ → 粗利↑ → 業績の上方修正の期待 | 不祥事 → アクティビスト → 過去の投資先の型 → 似た会社 |
| 証拠 | 有報のセグメント、取引先、原価構成 | テーマ分類、過去事例、報道の見出し |
| 特徴量 | `economic_impact` | `investor_salience` |

各エッジには `relation`、`direction`、`strength`、`evidence[]`、`confidence` を持たせる。同じ候補が両方のグラフから出てくるか、片方だけから出てくるかも特徴量(`graph_source`)として保存する。

### 7.3 候補を生成する経路の型

`direct`(直接)/ `second_order`(2段目)/ `third_order`(3段目)/ `supply_chain`(サプライチェーン)/ `substitution`(代替)/ `competition`(競合)/ `policy`(政策)/ `investor_psychology`(投資家心理)/ `historical_analogy`(過去の類似事例)/ `activist_mna`(アクティビスト・M&A)

連想の段数(`association_distance`)は経路の型とは別に数値で持つ。

追加の型:

- `scheduled_event`(予定イベントへの先回り):選挙、政策の施行日、大型催事など、日程が分かっている出来事への連想。「噂で買って事実で売る」型の検証のため、`days_to_scheduled_event`(予定日までの営業日数)を特徴量として持つ。

**方向**:各候補は `side` として `long`(上昇)か `caution`(下落・警戒)を持つ。下がる連想も記録するのは、次の2つのためである。
- 連想の方向が当たっているかを検証する
- 保有銘柄への警告に使う(既存システムへの参考情報)

`caution` の候補は本命(A)には入れず、レポートの「警戒リスト」に表示する。

### 7.4 証拠の照合と反証

各候補について、次の質問に答えさせる。

1. 本当にこの会社はイベントの影響を受けるか(企業資料で確認できるか)
2. 影響は利益に対して十分な大きさか
3. **影響の方向は正しいか。**プラスにもマイナスにも読める場合は、`direction_ambiguity` を立てる(例:半導体不足で任天堂は、品薄=需要が強いとも読めるし、作れない=売上減とも読める)
4. 時間軸は妥当か(効果の発現が遅すぎないか)
5. 他社のほうがより大きく恩恵を受けないか
6. すでに市場で認識されていないか
7. 投資家の注目がすでに過剰ではないか

証拠の強さは `Strong / Medium / Weak / None` の4段階とする。**None でも候補から消さない。** 証拠のない連想が上がるかどうか自体が、検証すべき問い(中心仮説1)だからである。

### 7.5 仮説(Thesis)の段階的な強化の追跡

#### 目的

1つの仮説が、複数のニュースによって段階的に強くなっていく流れを追う。イベントを1件ずつ独立に扱うと、この流れが見えなくなる。

例(アクティビスト型):

```
Thesis「アクティビストが入り、株価が上がる」
 ├ 段階1: 不祥事の報道          → 強さ Weak    (連想だけ)
 ├ 段階2: スポンサー離れ        → 強さ Weak+   (経営が弱っている事実)
 ├ 段階3: 株主提案・発言        → 強さ Medium  (アクティビストが実在)
 └ 段階4: 大量保有報告書の提出  → 強さ Strong  (一次情報で確定)
```

#### 仕組み

1. **仮説を独立した記録にする**(§5.3 の `thesis` / `thesis_update`)。段階の履歴は追記のみとし、過去の段階を書き換えない。
2. **毎晩の照合(⑤')**:入力パックに進行中の仮説の一覧を含める。LLMは各イベントについて、次のどれに当たるかを判定する。
   - `reinforce`(強化):仮説を支える**新しい事実**が加わった
   - `weaken`(弱体化):仮説に反する事実が加わった
   - `neutral_repeat`(繰り返し):既知の事実の再報道・論評だけ
   - `kill`(消滅):仮説が成り立たなくなった(例:アクティビストが株を売却した)
   - 該当なし → 新しい仮説として `open` するか、無関係とする
3. **その日のうちに紐づける。** 過去のイベントを後から仮説に紐づけることは禁止する(§14)。後から紐づけると、結果を知ったうえでの後付けになるためである。
4. **新しい事実と繰り返しを区別する。**
   - 同じ事実を10社が報じても、それは注目度の増加(§6)であって、仮説の強化ではない。
   - `reinforce` として認めるのは、次の2つを満たす場合だけとする。
     - 証拠のURLが1件以上ある
     - 事実の要約のハッシュ(`new_fact_hash`)が既存の段階と重複しない
   - 満たさない場合は、Python 側で `neutral_repeat` に格下げする。
5. **確証バイアスへの対策**:
   - LLMは一度立てた仮説を強める方向に解釈しがちである。そのため、各イベントについて強化と弱体化の**両方の読み方**を必ず出させ、そのうえでどちらかに判定させる。
   - `reinforce` の判定には、必ず `counter_note`(その強化が見かけだけである可能性)を付ける。
6. **自動での休眠と消滅**:最後の更新から一定期間(暫定20営業日、§15)`reinforce` がない仮説は `dormant`(休眠)にする。休眠中の仮説が再び強化されたら `active` に戻し、戻ったことを記録する。

#### 強さの段階

`Weak`(連想のみ)→ `Weak+`(状況証拠が1つ)→ `Medium`(関係者の実在・言動が確認できる)→ `Strong`(一次情報で確定)

仮説の強さ(`current_strength`)は、個々の候補の証拠の強さ(`evidence_strength`)とは別に持つ。

### 7.6 【関門2】候補の格付け(量より質・その2)

候補は全件記録する。ただし、**あなたが見るべき本命は1日0〜3件に絞る。**

| 格付け | 条件(暫定。§10.4 で事前に固定) | レポートでの扱い |
|---|---|---|
| **A 本命** | 以下をすべて満たす候補の上位3件まで:①イベントが関門1の条件1〜3のどれかで通過 ②`side=long` ③方向が曖昧でない ④証拠の強さが Medium 以上、または仮説の強さが Medium 以上 ⑤まだ織り込まれていない(`awareness_gap` が大きい) ⑥株価状態が Highly Extended でない ⑦流動性の下限を満たす | 先頭に詳しく表示 |
| **B 監視** | A の条件のうち1〜2個を欠くもの | 一覧で表示 |
| **C 記録のみ** | それ以外 | 表示しない。記録と評価だけ行う |

#### 「上がる確度が高い銘柄」の中身

確度を上げる要素として、次を特徴量に加える(§8.1)。

1. **テーマ純度**:その事業が売上に占める比率(有報のセグメントから)。大企業の一部門より、**その事業が主力の小型株**のほうが大きく動く。
2. **時価総額の小ささ**:同じ材料でも、小型株ほど値動きが大きい。ただし流動性の下限とセットで扱う。
3. **物語の分かりやすさ**:一言で説明できる連想ほど、市場が乗りやすい。
4. **仮説の強さ**:段階的に強化されている仮説の銘柄(§7.5)。
5. **需給の初動**:出来高が増え始めているが、株価はまだ大きく動いていない状態。

#### 格付け自体も検証する

格付けは仮説である。**A の成績が B を、B の成績が C を上回るか**を §10.2 で検証する。上回らなければ、格付けの条件のほうが間違っている。

### 8.2 表示用の暫定ランキング

特徴量が貯まるまでの間、日次レポートの並び順だけは次の暫定式で決める。

```
暫定順位 = attention(加速を含む) × investor_salience × awareness_gap
          × theme_purity × thesis_strength の補正
          × (1 − direction_ambiguity の減点)
```

- これは**表示の並び順にすぎず、有効性の主張ではない。**
- 掛け算にしているのは、どれか1つがゼロなら順位を下げるためである。
- 重みはフェーズ4で、結果との関係を見てから決め直す。

## 9. 予測・対照群・事例集

### 9.1 予測スナップショット

- ⑩ で確定する。`input_pack_hash` によって、どの入力から生まれた予測かを追跡できるようにする。
- 確定後の書き換えは禁止する。判断を変えるときは `version+1` を新しい行として追記する。
- 1つのイベントから出る候補の上限は**5銘柄**とする(暫定)。候補が多すぎると質が落ち、イベント単位の評価でも比較しにくくなる。
- 仮説が強化されたとき、その仮説の対象銘柄については**新しい段階の予測を新しい行として追記する**(`thesis_stage` を更新)。前の段階の予測はそのまま残す。これにより、段階ごとに入った場合の結果を比較できる。

### 9.2 結果の評価(⑬ で毎日自動更新)

- 期間:1 / 3 / **5 / 10 / 20** / 60D。120 / 252D は算出だけする。
- 指標:絶対リターン、TOPIX超過(1306.T で代用)、業種超過、MFE(期間中の最大含み益)、MAE(期間中の最大含み損)、期間内の最大リターン。
- 時刻:イベントの時刻、候補の発見時刻、初めて大きく値が動いた日、+5% / +10% に達するまでの日数。これらから先行日数を出す。

#### 約定可能性(テーマ株で最重要)

テーマ株は、翌朝ストップ高の気配のまま買えないことが多い。「翌営業日の始値で買えた」と仮定すると、**最も上がった銘柄ほど実際には買えていない**ことになり、成績が水増しされる。

- 翌営業日の始値・高値・安値・終値がすべて制限値幅の上限(ストップ高)に一致する場合は、**買えなかった(`unfilled`)**とする。値幅制限の表は JPX の規則に従って実装する。
- 買えなかった場合は、翌々営業日の始値で買えたとする結果(`delayed`)も併記する。本評価は「買えなかった分を除いた成績」と「遅れて買った成績」の両方で報告する。
- 売りも同様に扱う。ストップ安で売れない日は持ち越したものとする。
- コスト:往復の手数料とスプレッドを差し引いた `ret_net` を主指標とする。スプレッドは売買代金の帯ごとの暫定値を使う。

#### 出口の模擬比較

出力は候補までだが、**出口の仮説を検証するため、模擬的な出口ルールで結果を計算する**(売買の指示ではない)。

| ルール | 内容 |
|---|---|
| `fixed_5/10/20` | 5・10・20営業日後の終値で手仕舞い |
| `attention_fade` | イベントの注目度が `Fading` に入った翌営業日の始値 |
| `thesis_kill` | 仮説が `weaken` または `kill` になった翌営業日の始値 |
| `stop_-10` | 終値ベースで −10% を割った翌営業日の始値 |

### 9.3 対照群(予測時に自動抽出)

候補1銘柄につき、次の対照を Python が乱数の種を固定して抽出する。

| 対照の型 | 内容 |
|---|---|
| `same_event_rejected` | 同じイベントでLLMが検討したが、候補にしなかった銘柄(LLMに出力させる) |
| `same_industry_matched` | 同じ業種(東証33業種)で、時価総額の帯と株価状態が近い銘柄 |
| `random_matched` | 全銘柄から、時価総額の帯と株価状態を揃えて無作為に選んだ銘柄 |
| `unreinforced_thesis` | 仮説単位の対照。一度も `reinforce` されずに休眠・消滅した仮説の段階1の予測。強化された仮説の段階1と比べる |

**予測時に抽出しておくのが肝心である。** 後から選ぶと、結果を見て都合の良い対照を選んでしまう余地が生まれる。

### 9.4 事例集(発見用・事後分析)

- 過去の大ニュースと連想相場の事例を30〜50件、`expost/cases/` に Markdown と JSON で蓄積する。
- 各事例には、イベント、注目度の曲線(GDELT・Wikipedia)、連想の経路、上がった銘柄と**上がらなかった関連銘柄**を記録する。
- 用途は**仮説を作ることと、プロンプトに与える型の例示**に限る。有効性の証拠には使わない(§2.3 の落とし穴1)。
- 事例をプロンプトに入れるときは、「事例から得た型」だけを抽象化して渡す。個別の結末(何倍になったか)は渡さない。

### 9.5 単純な方法との比較(最重要)

「連想で選んだ銘柄が上がった」だけでは、連想に価値があるとは言えない。**単純な方法でも同じ成績が出るなら、LLMで連想する意味はない。** そこで、次の単純な方法の候補を毎日同時刻に機械的に記録し(`baseline_pick`)、同じ約定ルール・同じコスト・同じ件数で評価する。

| 比較対象 | 内容 |
|---|---|
| `volume_surge` | 出来高倍率の上位(流動性の下限を満たすもの) |
| `momentum_5d` | 5日上昇率の上位 |
| `attention_direct` | 関門1を通ったイベントの**直接の関連銘柄だけ**(連想をしない場合) |
| `theme_rank` | 人気テーマ上位の構成銘柄(取得が利用規約上可能な場合のみ) |
| `existing_supply_demand` | 既存の需給システムの当日の出力(読み取り専用。フェーズ0で可否を確認) |

あわせて、**本命(A)と各比較対象との銘柄の重なり**も記録する。重なりが大きければ、連想は既存の方法と同じものを別の道で見つけているだけである。

### 9.6 あなた自身の判断の記録

候補の中から最終的に選ぶのはあなたである。日次レポートの各候補に「買う/監視/見送り」と一言の理由を付けられるようにし、Python が取り込んで `user_decision` に記録する。

- これにより、「モデルが出した全候補」と「あなたが選んだ候補」の成績を比べられる。
- あなたの判断がモデルを上回る型が分かれば、それをモデルに取り込む材料になる。下回る型が分かれば、自分の癖を知る材料になる。

## 10. 検証計画

### 10.1 検証の原則

- **有効性の判断に使うのは、前向きに記録したスナップショットだけ**とする。
- 過去事例での「再現率」は参考値として別枠で報告し、有効性の根拠にはしない。

### 10.2 優先して検証する問い

1. 2段目の連想は、直接の連想より超過リターンが大きいか
2. 注目度が Rising のイベントの候補は、Flat のイベントの候補より良いか(中心仮説2・3)
3. `awareness_gap`(未織り込み度)は効くか
4. 投資家連想グラフと経済グラフでは、どちらの候補が良いか。両方から出た候補はさらに良いか
5. 証拠の強さは結果と関係するか
6. 注目度が Fading に入ったあとの候補リターンは落ちるか(出口の仮説)
7. イベントの型によって効き方は違うか
8. **仮説のどの段階で入るのが最も良いか。** 段階1(安く買えるが外れやすい)か、確定段階(確実だが織り込み済み)か
9. **市場が最も大きく反応するのはどの段階か。** 最初の報道か、決定的な一次情報か
10. **強化の間隔が短い(立て続けに強化される)仮説は、結果が良いか**
11. **強化された仮説の段階1と、強化されなかった仮説の段階1では、段階1の時点で見分けがつくか。** 見分けがつくなら、段階1で入る判断の精度を上げられる
12. **【最重要】本命(A)は、単純な方法(§9.5)をコスト控除・約定可能性込みで上回るか。** これが否定されたら、本モデルの存在意義がない
13. **格付けは機能しているか。** A > B > C の順に成績が並ぶか
14. **テーマ純度と時価総額の小ささは効くか**
15. **関門1で落としたイベント(`gate_audit`)の候補は、通過したイベントの候補より本当に劣るか**
16. **あなたが選んだ候補は、選ばなかった候補より良いか**
17. **出口ルールの比較**:`attention_fade` や `thesis_kill` は、固定期間の保有より良いか
18. **警戒(`caution`)の連想は、実際に下落・劣後しているか**(方向の的中率)
19. **地合いによって効き方が変わるか**
20. **予定イベントへの先回り(`scheduled_event`)は、予定日の何日前に入るのが良いか。予定日を過ぎると反落するか**

### 10.3 統計の扱い

- **集計の単位はイベント**とする。候補の件数で有意性を判断しない。
- 層別(イベントの型、連想の段数、注目度の局面、時価総額の帯など)の結論は、**その層に独立したイベントが30件以上**揃うまで出さない。
- 必要期間の見積もり:実運用で1日1〜3イベントなら、主な問い(12・13・1〜3)に最初の答えが出るまで**約3〜6か月**かかる。これは収集を今すぐ始める理由でもある。
- 信頼度の較正:`confidence` の帯ごとに、実際の的中率を比較する。

### 10.4 判断基準の事前固定と撤退基準

特徴量と層が多いので、たくさん試せば、偶然「効いている」ように見えるものが必ず出てくる。これを防ぐため、次のようにする。

1. **分析計画を先に書いて固定する**:フェーズ2の終了時点(本格的な記録の開始前)に、`docs/ANALYSIS_PLAN.md` を作って git に記録する。中身は次のとおり。
   - 主に検証する問い(§10.2 の 12・13・1・2・3 を優先)
   - 評価指標(20日のコスト控除後・TOPIX超過リターンの中央値 など)
   - 合格の基準
   - 関門1・2の閾値
   - 以後の変更は、日付と理由を付けて追記する。
2. **発見と確認を分ける**:記録期間の前半で見つけた傾向は「探索的な発見」とし、後半の期間で再現した場合だけ「確認済み」とする。
3. **閾値を変えたら区切る**:関門の閾値やプロンプトを変えた日以降は別の期間として扱い、変更前後の成績を混ぜない。
4. **撤退基準(暫定)**:次のどちらかを満たしたら、本モデルの中止または方針転換を検討する(数値は §15 で確定する)。
   - 記録開始から6か月、かつ本命(A)の独立したイベントが60件以上たまった時点で、問い12(単純な方法を上回るか)が否定された場合
   - 問い13(格付け)で、A が C を上回らない場合

### 11.1 ディレクトリ(案)

```
association-model/            ← 既存システムとは別のフォルダ(またはリポジトリ)
├── docs/                     設計書・判断記録
├── config/                   RSS一覧、パス設定(既存の株価DBの場所など)
├── schemas/                  JSONスキーマ
├── prompts/                  LLMプロンプト(版管理)
├── .claude/commands/         /association-daily など
├── src/
│   ├── ingest/               RSS / GDELT / TDnet / EDINET / Wikipedia
│   ├── attention/            注目度の計測
│   ├── market/               既存のyfinanceデータの読み取りと銘柄状態の計算
│   ├── pack/                 日次入力パックの生成
│   ├── commit/               スキーマ検証とスナップショットの確定
│   ├── controls/             対照群の抽出
│   ├── gates/                関門1(イベントの足切り)・関門2(格付け)
│   ├── baselines/            単純な方法の候補の記録
│   ├── master/               銘柄マスタ・別名辞書・上場銘柄一覧・データ品質チェック
│   ├── thesis/               仮説の状態管理(段階の追記・休眠化)
│   ├── outcome/              結果の追跡
│   └── report/               日次レポートの生成
├── expost/cases/             事例集(git管理・小さい)
├── tests/
└── data/                     ← .gitignore(DuckDB・生データ・レポート)
    └── predictions/          ← スナップショット(別途バックアップ)
```

### 11.2 日次の運用

```
18:00  [自動] 収集・注目度・銘柄状態・入力パックの生成(タスクスケジューラ)
20:00〜 [手動] Claude Code で /association-daily を実行 → JSON出力
       [自動] 確定・対照群の抽出・レポートの生成(コマンドの最後に呼ぶ)
翌 7:30 [任意・手動] 夜間の差分を確認
毎日   [自動] 結果の追跡を更新
```

LLMの手順を実行しなかった日も、収集だけは自動で続ける(落とし穴2への対策)。

#### 手動作業の上限と、実行しなかった日の扱い

- **1回あたり15〜30分**に収まるよう、関門1で件数を絞る(§6.4)。30分を超える日が続く場合は、閾値を見直す。
- **最小手順(`minimal`)**:時間がない日は、進行中の仮説の更新確認と、注目度1位のイベントだけを処理する。10分以内を目安とする。
- **実行記録(`run_log`)**:実行したか、どの手順か、所要時間、見送った理由を毎日記録する。
- **見送りの偏りの点検**:見送った日の注目度の分布と、実行した日の分布を比べる。大ニュースの日ほど見送っている、といった偏りがあれば、成績の評価が歪むので報告する。

### 11.3 バックアップ

`data/predictions/*.jsonl` だけは、git 以外の場所(クラウドストレージなど)にも日次で複製する。このファイルは再生成できず、検証データの本体だからである。

### 11.4 クラウドとローカルの受け渡し

- コード・設計書・プロンプトは、このリポジトリで管理し、ローカルでは `git pull` で受け取る。
- データはリポジトリに入れない。どちらの環境でも、スクリプトでデータを作り直せるようにする。

## 14. 禁止事項

- 未来の情報の混入(LLMの知識による混入を含む)
- 勝ち銘柄だけでの学習・結論
- 事後の説明(ナラティブ)を過去の予測に混入させること
- LLMの推論を証拠として扱うこと
- スコアを作っただけで有効性を主張すること
- 少ないサンプル(独立したイベントが30件未満の層)からの一般化
- SNSや検索量を事実として扱うこと
- 既存モデルのコード・既存データの変更や上書き
- 未検証の指標を既存システムの判断に入れること
- 確定済みスナップショットの書き換え
- 過去のイベントを後から仮説に紐づけること、仮説の段階の履歴の書き換え
- 買えなかった(ストップ高で寄らなかった)銘柄を、買えたものとして評価すること
- 単純な方法との比較を省いて有効性を主張すること
- 分析計画にない問いの結果を、「探索的」と明記せずに報告すること
- 結果を見てから関門の閾値を変え、変更前の期間と混ぜて評価すること
